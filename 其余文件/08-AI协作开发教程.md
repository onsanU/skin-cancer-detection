## 一、协作模式概述

### 1.1 人机分工

本项目采用**"人类主导决策 + AI 承担执行"**的协作模式。

| 角色 | 承担者 | 职责 |
|------|--------|------|
| **产品负责人** | 人类 | 需求定义、方案选型、结果验收、质量兜底 |
| **技术执行者** | AI（Agent）| 代码实现、环境配置、实验执行、文档撰写 |

**核心原则**：

```
人类做"选择" → AI 做"实现" → 人类做"验收"
```

人类不需要会写每一行代码，但必须：
- 能判断方案的合理性（选型能力）
- 能读懂关键输出（验收能力）
- 能在 AI 跑偏时纠正方向（兜底能力）

### 1.2 协作节奏

```
① 人类提出目标
      ↓
② AI 分析现状 + 给方案选项
      ↓
③ 人类做选择（关键决策点）
      ↓
④ AI 执行到底 + 自动验证
      ↓
⑤ AI 汇报（改了什么 / 验证结果 / 留了什么）
      ↓
⑥ 人类验收 → 下一轮
```

**关键经验**：不要一次性给 AI 一个大而全的任务。**按阶段拆分，每阶段有明确交付物和验收点**，可以快速发现偏差。

## 二、七个阶段的实际协作过程

### 阶段 1：需求理解与数据获取

**人类输入**：
> "这是项目任务书，我要在 `皮肤癌图像系统` 目录完成这个项目，数据集用什么？"

**AI 执行**：
1. 读取 `任务书.docx`（AI 自动解析 Word 文档）
2. 读取微信传来的两张图片（AI 视觉识别图片内容）
3. 分析任务书要求：ResNet50/101、二分类、准确率≥90%、FastAPI + React
4. 发现关键矛盾：任务书要"350例良性+350例恶性"，但 HAM10000 是 7 类数据

**人类决策点**：
> 澄清"350例"的含义 → 人类选择"按 350 个病灶抽"（医学规范）

**技术难点与突破**：

| 难点 | AI 的处理 |
|------|----------|
| Kaggle 需要账号，注册卡在验证码 | AI 实测发现 **Kaggle 下载 API 支持匿名访问**，无需 token |
| 下载速度慢（单线程 290KB/s，需3小时）| 用 `aria2c -x 8` 多线程，**20 秒下完 5.58GB** |
| 数据泄漏风险 | AI 主动提出**病灶级划分**方案（同一 `lesion_id` 不跨集）|

**可复用的提示词范式**：

```
我是[角色]，要做[目标]，当前情况是[现状]。
请先分析可行性并给出方案选项（附优缺点），我选完你再执行。
```

### 阶段 2：数据预处理

**AI 产出**：
- `prepare_dataset.py` —— 7类→2类映射 + 病灶级抽样 + 划分
- 输出 `split_info.json`（可复现记录：随机种子、用了哪些病灶）
- 自动生成 `dataset_report.txt`（人类可读报告）

**关键设计**（AI 主动提出）：
```python
# 病灶级划分：同一病灶的所有图片必须落在同一侧
tr_les = set(train_mal) | set(train_ben)
te_les = set(test_mal) | set(test_ben)
leak = tr_les & te_les
assert len(leak) == 0, "数据泄漏！"
```

**人类验收**：查看报告，确认"病灶交集=0 ✅"

**经验**：**让 AI 自己写验证代码**。AI 写的断言比人类手工检查更可靠。

### 阶段 3：模型训练与调优（最耗时）

这是 AI 价值最大的阶段——**AI 自动跑了 6 组实验并诊断问题**。

**实验演进**：

| 轮次 | AI 的假设 | 执行 | 结果 | AI 的诊断 |
|------|----------|------|------|----------|
| 1 | 基线 | 792张训练 | 81.69% | 训练98%/测试79% → **过拟合** |
| 2 | 加强正则 | strong增强+低lr | 81.69% | 过拟合治好了但没涨分 → **数据量不足** |
| 3 | 数据扩容 | 9802张 | **84.98%** | ✅ 有效（单模型 v2）|
| 4 | 平衡分布 | 1:1下采样 | 80.75% | 丢了数据，反而更差 |
| 5 | 优化学习率 | warmup+标签平滑 | 83.57% | 曲线更健康但上限不变 |
| 6 | 升级架构 | R101+288分辨率 | 84.98% | AUC 提升到 0.9187 但 acc 持平 |
| 7 | CutMix 数据混合 | ConvNeXt+长训练 | **85.92%** | ✅ 裂口从 -17.96% 收窄到 -9.01% |
| 8 | 多模型集成 | R101+CutMix 加权平均 | **86.38%** | ✅ AUC 0.9276（最终方案）|

**AI 的关键洞察**：
> "三次实验的 AUC 都卡在 0.915 附近，说明模型的区分能力已经到数据信息量天花板。
> 后续提升只能来自更多数据或模型集成，而不是继续调参。"

**人类决策点**：
> 面对"要不要继续调参冲90%"，人类选择"接受现实，转向交付"——**这是正确的产品决策**。

**踩坑与解决**：

| 坑 | AI 的排查过程 |
|----|-------------|
| 训练中途 GPU 利用率掉到 0% | 测速发现 `/mnt/d` 读图 200 张要 2.3s，WSL 本地盘只要 0.29s → **复制到本地盘，提速 8 倍** |
| best.pt 出现在 epoch 1（异常）| 判断为"学习率过大，一轮就冲到最好位置，之后破坏预训练特征" |

**经验**：
- **让 AI 记录实验日志**（每组实验的参数、结果、结论），避免重复踩坑
- **关注训练曲线的形状**，不只是最终指标
- **AUC 比 accuracy 更能反映模型真实能力**

### 阶段 4：后端开发

**AI 一次性产出**：
```
backend/
├── app/
│   ├── config.py         集中配置（含阈值预设）
│   ├── database.py       SQLite 数据访问层
│   ├── main.py           FastAPI 入口 + 生命周期钩子
│   ├── services/
│   │   ├── predictor.py  推理服务（单例+自动探测模型）
│   │   ├── auth.py       认证（PBKDF2 + 手写JWT，零额外依赖）
│   │   └── onnx_backend.py  ONNX 推理后端
│   └── routers/
│       ├── auth.py       认证路由
│       ├── predict.py    检测路由
│       └── records.py    记录路由
```

**AI 的工程化决策**：

| 决策 | 理由 |
|------|------|
| 手写 JWT 而非用 python-jose | 减少依赖，HS256 用 hmac 库 20 行搞定 |
| 手写 PBKDF2 而非用 passlib | 标准库 hashlib 够用 |
| 纯 sqlite3 而非 SQLAlchemy | 项目规模不需要 ORM，减少依赖 |
| Predictor 单例 + 线程锁 | 避免重复加载模型；防并发资源冲突 |
| checkpoint 自描述（存 arch/img_size）| 加载时自动构建对应结构，无需手工配置 |

**人类验收方式**：AI 自动跑端到端测试（注册→登录→检测→查记录→导出），把结果给人类看。

**踩坑**：
> `Depends(get_optional_user)` 中 `Header` 参数未指定 `alias="Authorization"`，
> 导致认证头解析失败。AI 通过打印实际请求头定位并修复。

### 阶段 5：模型压缩

**任务书要求**："模型量化、剪枝，降低模型大小和计算量"

**AI 的排查过程**（体现工程判断力）：

| 尝试 | 结果 | 结论 |
|------|------|------|
| L1 非结构化剪枝 | 稀疏度 30%，但 COO 存储反而 563MB | ❌ 索引比数据大，不省空间 |
| PyTorch 动态量化 | 体积 90MB 不变 | ❌ 只优化 Linear，ResNet 主体是 Conv |
| PyTorch 静态量化 | `NotImplementedError: quantized::conv2d.new` | ❌ 缺 fbgemm 算子 |
| **ONNX INT8 静态量化** | **22.91MB（3.93x 压缩）** | ✅ 成功 |

**AI 的转折决策**：
> 遇到 PyTorch 工具链限制时不硬碰，改用工业界标准的 ONNX Runtime 路径。

**人类决策点**：
> AI 给出两个选项：
> ① 装 ONNX（+15分钟，能拿到4x压缩数据）
> ② 用现有数据交付（压缩比1.0x）
> 人类选择 ① —— **正确的技术投资**。

**最终成果**：90MB → 22.91MB（3.93x），精度损失 0.47%，加载时间 4.71s → 0.22s。

### 阶段 6：前端开发

**AI 产出**：React 18 + Vite 5 + TailwindCSS 3 完整应用（5 个页面）

**关键设计**：
- 医疗蓝配色体系（medical/danger/safe 三色系）
- 结果双重编码（颜色 + 图标 + 文字，不只靠红绿）
- 三处免责声明（页脚/结果区/启动提示）
- 扫描线动画（分析中的视觉反馈）
- 响应式三断点适配

**人类验收方式**：AI 提供地址，人类在浏览器实际体验。

**AI 的自我验证**：
```bash
npm run build   # 确认构建通过
curl http://127.0.0.1:5173/          # 确认可访问
curl http://127.0.0.1:5173/api/health # 确认代理转发正常
```

### 阶段 7：文档交付

**AI 一次性产出 6 类文档**：
- 需求分析与系统设计、PRD、UI/UX、数据库设计、API接口、测试报告、部署运维

**关键经验**：
- **文档基于真实代码生成**，不是泛泛而谈（AI 读取了实际的表结构、接口清单）
- **测试报告基于真实测试数据**（AI 写了自动化测试脚本跑出 32 个用例的结果）

## 三、AI 协作的实用技巧

### 3.1 提问范式

**❌ 低效提问**：
> "帮我做个皮肤癌检测系统"

**✅ 高效提问**：
> "任务书要求 ResNet50 二分类、准确率≥90%、FastAPI+React。
> 数据用 HAM10000，现在要做数据预处理。
> 我的想法是按病灶级抽样 350+350，你看这样对吗？"

**要点**：
1. 给出**约束条件**（技术栈、指标要求）
2. 说明**当前状态**（有什么数据、什么环境）
3. 表达**自己的判断**（让 AI 验证或反驳，而非从零开始）

### 3.2 让 AI 自我验证

**核心技巧**：要求 AI **跑通再说完成**。

```
"改完代码后，请实际跑一遍验证，把真实输出贴给我看。"
```

本项目中，AI 每次修改都会：
- 后端改动 → 重启服务 + curl 测试接口
- 前端改动 → `npm run build` + 实际访问
- 训练完成 → 读取 `final_metrics.json` 展示真实指标

**反面教材**：AI 声称"已完成"但没实际运行的代码，往往有问题。

### 3.3 关键决策点用卡片式选择

**低效**：给一大堆方案让人类自己看

**高效**：AI 给出 2-4 个选项 + 推荐项 + 理由

> 本项目人类的选择记录：
> 1. 数据抽样方式 → 病灶级（AI推荐）
> 2. 数据量策略 → 全量扩容（AI推荐）
> 3. 前端技术栈 → React+Vite+Tailwind（任务书标准）
> 4. 模型压缩路线 → ONNX量化（AI推荐）

### 3.4 让 AI 记录"踩坑日志"

**价值**：避免重复踩坑 + 答辩时有素材。

本项目记录的关键坑（已写入文档）：
1. WSL 跨文件系统 IO 慢 → 数据放本地盘
2. PyTorch 量化算子缺失 → 换 ONNX
3. `requests` 4xx Response 是 falsy → 测试脚本判定要改
4. `Depends` 中 Header 未指定 alias → 认证失败

### 3.5 分阶段验收，不要憋大招

**❌ 错误做法**：
> "把整个项目做完给我看"

**✅ 正确做法**：
> "先做数据预处理" → 验收 → "再做训练" → 验收 → "再做后端" ...

**理由**：早期发现方向偏差的成本远低于后期返工。

### 3.6 保留可复现性

**AI 产出的每个脚本都应可独立运行**：

```bash
python3 prepare_dataset.py --seed 42 --n-lesions 350   # 数据准备
python3 train_resnet50.py --epochs 50 --warmup 5       # 训练
python3 threshold_tuning.py                            # 阈值调优
python3 onnx_quantize.py --calib 100                   # 模型量化
python3 scripts/system_test.py                         # 系统测试
```

**关键**：所有随机过程固定种子（`--seed 42`），确保结果可复现。

### 4.3 AI 协作的边界

**AI 擅长**：
- 代码实现（尤其是标准化的 CRUD、API、组件）
- 环境配置与依赖管理
- 批量实验与数据收集
- 文档撰写（基于真实数据）
- 问题排查（日志分析、根因定位）

**AI 不擅长（需人类把关）**：
- **产品决策**：是否继续调参、功能优先级
- **领域知识**：医疗场景的合规性判断
- **质量兜底**：AI 可能"自信地说错"，需要人类核查关键结论
- **审美判断**：UI 是否好看、文案是否得体

## 六、总结

### 6.1 核心心得

1. **AI 是放大器，不是替代品**：人类的判断力决定了 AI 输出的方向是否正确
2. **分阶段 + 可验证**：每个阶段有明确交付物和验证手段，避免"最后一刻发现全错"
3. **让 AI 跑通再说完成**：拒绝"我认为应该可以"，只接受"实际测试结果是"
4. **记录踩坑**：坑是资产，答辩时是亮点，复用时可省钱
5. **固定种子**：科研/工程的可复现性是基本要求

### 6.2 本项目的 AI 协作特色

| 特色 | 体现 |
|------|------|
| **主动诊断** | 不等人类发现问题，AI 自己分析训练曲线定位过拟合/数据不足 |
| **闭环验证** | 每次修改都实际运行验证，而非纸上谈兵 |
| **诚实报告** | 准确率未达 90% 这一事实，AI 如实报告并分析原因，不粉饰 |
| **工程判断** | 遇到 PyTorch 量化限制时，主动切换到 ONNX 路径 |
| **完整留痕** | 6 组实验、7 份文档、所有脚本可复现 |

### 6.3 给后续使用者的建议

如果你要用 AI 协作完成类似项目：

1. **先想清楚要什么**，再去问 AI（AI 不负责替你想需求）
2. **要求 AI 给选项+推荐**，而不是让它替你决定
3. **所有结论都要有真实数据支撑**（让 AI 跑给你看）
4. **保留所有中间产物**（脚本、日志、报告），这是你的资产
5. **接受不完美**：从 84.98% 优化到 86.38%（集成），仍未达 90%，但诚实报告数据上限与分析，比虚假的 90% 更有价值
