## 一、设计概述

### 1.1 选型理由

| 考量 | SQLite 的优势 |
|------|-------------|
| **部署简易** | 单文件数据库，零配置、零运维 |
| **项目规模适配** | 单机部署、中小规模并发完全够用 |
| **数据完整性** | 支持事务（ACID）、外键约束 |
| **备份便捷** | 复制单个 `.db` 文件即完成备份 |
| **无依赖** | Python 标准库内置 `sqlite3`，无需额外服务 |

**适用性说明**：本项目为课程实践/单机部署场景，SQLite 足够。若未来需要多用户高并发，可平滑迁移至 PostgreSQL/MySQL（ORM 层已抽象数据访问）。

### 1.2 存储结构

```
backend/
├── skin_cancer.db          SQLite 主数据库
├── skin_cancer.db-wal      WAL 日志（预写式日志）
├── skin_cancer.db-shm      共享内存文件
└── uploads/                上传的原始图像
    ├── u1_20260914_144048_a3f2b1c9.jpg
    ├── u2_20260914_150312_7d8e4f2a.png
    └── guest_20260914_151204_9c1b5e6d.jpg
```

**文件命名规则**：`{用户标识}_{时间戳}_{UUID前8位}{扩展名}`
- 用户标识：`u{user_id}` 或 `guest`
- 时间戳：`YYYYMMDD_HHMMSS`
- UUID：8位十六进制随机串（防重名冲突）

## 三、逻辑模型（表结构详述）

### 3.1 users 表（用户表）

| 字段名 | 类型 | 约束 | 说明 |
|--------|------|------|------|
| `id` | INTEGER | PK, AUTOINCREMENT | 用户主键 |
| `username` | TEXT | NOT NULL, UNIQUE | 用户名，登录凭证之一 |
| `email` | TEXT | NOT NULL, UNIQUE | 邮箱，可用于登录 |
| `password_hash` | TEXT | NOT NULL | 密码哈希（PBKDF2-SHA256）|
| `full_name` | TEXT | DEFAULT '' | 姓名/昵称，可空 |
| `role` ★ | TEXT | NOT NULL DEFAULT 'user' | **角色：`user`（普通用户）/ `admin`（管理员）** |
| `created_at` | TEXT | NOT NULL | 注册时间（YYYY-MM-DD HH:MM:SS）|
| `is_active` | INTEGER | NOT NULL DEFAULT 1 | 账号状态：1=启用, 0=禁用 |

**建表语句**：

```sql
CREATE TABLE IF NOT EXISTS users (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    username      TEXT    NOT NULL UNIQUE,
    email         TEXT    NOT NULL UNIQUE,
    password_hash TEXT    NOT NULL,
    full_name     TEXT    DEFAULT '',
    role          TEXT    NOT NULL DEFAULT 'user',   -- user / admin
    created_at    TEXT    NOT NULL,
    is_active     INTEGER NOT NULL DEFAULT 1
);
```

**字段设计说明**：

| 字段 | 设计考量 |
|------|---------|
| `password_hash` | 存储格式 `pbkdf2_sha256$120000${salt_b64}${hash_b64}`，包含算法、迭代次数、盐值、哈希值，便于未来升级算法 |
| 时间用 TEXT | SQLite 无原生日期类型；TEXT 存储 ISO 格式便于排序与人类可读 |
| `is_active` | 软禁用支持，避免物理删除导致的记录丢失 |
| `role` ★ | v1.1.0 新增。用 TEXT 而非 INTEGER 枚举，可读性优先（SQL 里直接能看懂）；管理接口统一用 `get_current_admin` 依赖校验，未登录 401 / 非管理员 403 |

**★ v1.1.0 幂等迁移（已存在数据库的兼容方案）**：

`CREATE TABLE IF NOT EXISTS` 对**已存在的表不会修改结构**，因此老库（本项目已有 33 用户 / 1408 记录）
必须通过迁移补列。`init_db()` 内挂 `_migrate()`，**每次启动幂等执行**：

```python
def _columns(conn, table: str) -> set:
    rows = conn.execute(f"PRAGMA table_info({table})").fetchall()
    return {r["name"] for r in rows}

def _migrate(conn):
    """轻量迁移：缺列则 ALTER TABLE 补上（每次启动幂等执行）"""
    cols = _columns(conn, "users")

    # 2026-09-14 管理后台迭代：users 加 role（user / admin）
    if "role" not in cols:
        conn.execute("ALTER TABLE users ADD COLUMN role TEXT NOT NULL DEFAULT 'user'")
        print("[DB] 迁移: users.role 已添加", flush=True)

    # 补齐业务不变量：如果没有管理员，把最早注册的账号提升为管理员
    row = conn.execute("SELECT COUNT(*) c FROM users WHERE role='admin'").fetchone()
    if row["c"] == 0:
        first = conn.execute(
            "SELECT id, username FROM users ORDER BY id ASC LIMIT 1"
        ).fetchone()
        if first:
            conn.execute("UPDATE users SET role='admin' WHERE id=?", (first["id"],))
            print(f"[DB] 迁移: 首个账号 '{first['username']}' 已提升为管理员", flush=True)
```

**迁移设计要点**：
- 新列带 `NOT NULL DEFAULT 'user'`，**已有行自动获得 `user` 角色，不需要回填**
- 每次启动执行且**幂等**（列存在则跳过，已有管理员则跳过）
- **SCHEMA 与迁移两处都要写**：全新部署走 SCHEMA 建表，老库升级走 `_migrate()`
- ⚠️ **本项目实际处理**：迁移起初把最早的测试残留账号 `testcat` 提为管理员（无人知道其密码），
  故后续**新建专用管理员账号 `admin`**（`create_user_ext(..., role="admin")`），并将 `testcat` 降回 `user`

### 3.2 records 表（检测记录表）

| 字段名 | 类型 | 约束 | 说明 |
|--------|------|------|------|
| `id` | INTEGER | PK, AUTOINCREMENT | 记录主键 |
| `user_id` | INTEGER | NOT NULL, FK | 所属用户 |
| `filename` | TEXT | NOT NULL | 用户上传时的原始文件名 |
| `stored_path` | TEXT | NOT NULL | 服务器磁盘存储路径 |
| `label` | TEXT | NOT NULL | 判定结果：`benign` / `malignant` |
| `label_cn` | TEXT | NOT NULL | 中文结果：`良性` / `恶性` |
| `probability` | REAL | NOT NULL | 判定类别的置信度（0~1）|
| `malignant_prob` | REAL | NOT NULL | 恶性概率（0~1）|
| `benign_prob` | REAL | NOT NULL | 良性概率（0~1）|
| `threshold` | REAL | NOT NULL DEFAULT 0.5 | 本次判定使用的阈值 |
| `infer_ms` | REAL | NOT NULL DEFAULT 0 | 推理耗时（毫秒）|
| `note` | TEXT | DEFAULT '' | 用户备注 |
| `created_at` | TEXT | NOT NULL | 检测时间 |

**建表语句**：

```sql
CREATE TABLE IF NOT EXISTS records (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id        INTEGER NOT NULL,
    filename       TEXT    NOT NULL,
    stored_path    TEXT    NOT NULL,
    label          TEXT    NOT NULL,
    label_cn       TEXT    NOT NULL,
    probability    REAL    NOT NULL,
    malignant_prob REAL    NOT NULL,
    benign_prob    REAL    NOT NULL,
    threshold      REAL    NOT NULL DEFAULT 0.5,
    infer_ms       REAL    NOT NULL DEFAULT 0,
    note           TEXT    DEFAULT '',
    created_at     TEXT    NOT NULL,
    FOREIGN KEY(user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

**字段设计说明**：

| 字段 | 设计考量 |
|------|---------|
| `label` + `label_cn` | 同时存英文标识（程序用）与中文（展示用），避免前端硬编码映射 |
| `probability` vs `malignant_prob` | 前者是"判定类别的置信度"（良性时=良性概率），后者固定为恶性概率。分开存便于统计与阈值再分析 |
| `threshold` | **记录判定阈值**是重要设计——医疗 AI 的阈值可调，留存阈值才能复现当时的判定逻辑 |
| `infer_ms` | 性能监控数据，可用于分析模型在不同图像上的耗时分布 |
| `stored_path` | 存完整路径，删除记录时可同步清理磁盘文件 |

### 3.3 索引设计

```sql
CREATE INDEX IF NOT EXISTS idx_records_user  ON records(user_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_records_label ON records(label);
```

| 索引 | 覆盖查询 | 设计理由 |
|------|---------|---------|
| `idx_records_user` | 某用户的历史记录按时间倒序 | **复合索引**：`user_id` 等值查询 + `created_at` 排序，一次索引扫描完成，避免额外排序 |
| `idx_records_label` | 按结果筛选（恶性/良性）| 提升筛选查询效率 |

**未建索引的字段及原因**：
- `filename`：不做搜索，无需索引
- `probability`：不做范围查询，无需索引

## 四、物理设计（存储与优化）

### 4.1 PRAGMA 配置

```python
conn.execute("PRAGMA journal_mode=WAL")    # 预写式日志：读写并发不阻塞
conn.execute("PRAGMA foreign_keys=ON")     # 启用外键约束（SQLite 默认关闭）
```

| 配置 | 作用 |
|------|------|
| `journal_mode=WAL` | 写操作不阻塞读操作，适合 Web 场景 |
| `foreign_keys=ON` | 启用外键级联删除，保证数据一致性 |

### 4.2 连接管理

```python
_local = threading.local()

def get_conn():
    """线程内复用连接（FastAPI 多线程环境下每线程独立连接）"""
    if getattr(_local, "conn", None) is None:
        _local.conn = _connect()
    return _local.conn
```

**设计要点**：
- SQLite 连接**不能跨线程共享**（默认限制）
- 使用 `threading.local()` 实现**线程级连接复用**，避免频繁创建开销
- `check_same_thread=False` 配合线程局部存储使用

### 4.3 事务管理

```python
@contextmanager
def tx():
    conn = get_conn()
    try:
        yield conn
        conn.commit()
    except Exception:
        conn.rollback()
        raise
```

**使用方式**：
```python
with tx() as conn:
    conn.execute("INSERT INTO records(...) VALUES(...)")
# 自动提交；异常时自动回滚
```

## 七、典型查询场景

### 7.1 查询用户历史记录（分页）

```sql
SELECT * FROM records
WHERE user_id = ?
ORDER BY created_at DESC, id DESC
LIMIT ? OFFSET ?;
```
→ 命中 `idx_records_user` 索引，避免全表扫描与额外排序

### 7.2 按结果筛选

```sql
SELECT * FROM records
WHERE user_id = ? AND label = ?
ORDER BY created_at DESC, id DESC
LIMIT ? OFFSET ?;
```

### 7.3 统计用户检测数据

```sql
SELECT label, COUNT(*) c
FROM records
WHERE user_id = ?
GROUP BY label;
```
→ 返回如 `{malignant: 5, benign: 7}`

### 7.4 导出用户全部记录

```sql
SELECT * FROM records
WHERE user_id = ?
ORDER BY created_at DESC
LIMIT 10000;
```

## 八、数据安全与隐私

| 措施 | 实现 |
|------|------|
| **密码保护** | PBKDF2-SHA256，12万次迭代，每用户独立随机盐 |
| **认证鉴权** | JWT（HS256），7天有效期，密钥可通过环境变量覆盖 |
| **越权防护** | 所有记录操作在 SQL 层强制 `user_id` 过滤 |
| **路径穿越防护** | 图片访问接口使用 `os.path.basename()` 过滤 |
| **文件类型校验** | 扩展名白名单 + MIME 类型双校验 |
| **文件大小限制** | 10MB 上限，超限立即删除临时文件 |
| **数据不外传** | 全部数据存储于本地，无第三方服务调用 |
| **级联清理** | 删除用户/记录时同步删除磁盘图片 |

## 十、扩展性设计

| 场景 | 扩展方案 |
|------|---------|
| 用户量增长 | SQLite → PostgreSQL，`database.py` 为唯一改动点 |
| 需要多设备登录 | 增加 `sessions` 表记录 refresh token |
| 需要记录修改历史 | 增加 `record_audit` 表，触发器写入 |
| 需要病变部位标记 | `records` 增加 `body_part` 字段 |
| 需要图像特征缓存 | 增加 `image_features` 表存 embeddings |
| 需要多模型对比 | 增加 `model_version` 字段记录推理所用模型 |
